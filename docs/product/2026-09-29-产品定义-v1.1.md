## 1. 一句话定义（更新）

**这是一个运行在你这台 Mac 上的个人 AI 能力操作台。**

它管三件事：
- 你有什么能力：资产层。
- 把能力交给谁、在哪里用：目标层。
- 让能力怎么跑起来：运行层。

一条进化回路把三层连起来：用过的留下证据，凭证据改版，新产生的方法收回来。

日常执行仍然在 Codex、Hermes、Claude 等原生 Agent 里进行。**工作台是你每天打开的那一个入口**，用来看安排、看待处理、找能力、交代任务、收成果。

与 v1.0 的差别：v1.0 强调“能力管理层”，v1.1 增加了“每天打开的入口”这个定位。这来自基线 D13 和 D17：以后都看工作台，工作台日历是你的时间规划本。

## 2. 产品骨架：三层 + 进化回路 + 贯穿能力

| 层 | 回答的问题 | 包含 | 与其他层的关系 |
|---|---|---|---|
| **资产层** | 我有什么 | Skill、Prompt、工作流（含协同模式）、规则模板、MCP 配置、逆向成果；知识的指针（正文在 Obsidian 或飞书） | 被目标层**安装或挂载**，被运行层**调用** |
| **目标层** | 交给谁、在哪里 | Agent 实例（配置、模型/API、挂载的 Skill、健康度），项目（身份、Current、协同协议） | 接收资产；为运行层提供执行者和工作现场 |
| **运行层**（harness） | 怎么跑起来 | 上下文接力、单目标执行、协同模式运行、夜间窗口、工作台日历（时间安排） | 按工作流的定义调度目标层；产出回到进化回路 |
| **进化回路** | 怎么越用越好 | 使用证据 → 改版候选 → 比较 → 采用或退回；日常新方法回收 | 读运行结果和反馈；写回资产层的新版本 |
| **贯穿能力** | 每层都要 | 版本（AI-Git）、搜索、待处理收件箱、能力体检、成本与用量、操作留痕、常驻与备份、安全准入 | — |

四条关键关系，也是 v1.0 没讲透的地方：

1. **协同模式属于工作流**，不是 Agent 中心的功能。Agent 中心负责提供和维护“人手”；工作流规定谁做什么、怎么交接；运行层负责让它真正跑起来。
2. **夜间不是独立系统。** 它等于运行层加上一个时间窗口、预算和晨间接管。
3. **日历是运行层的时间轴。** 你的规划、会议、项目里程碑、夜间窗口放在同一条时间线上。
4. **harness 的范围就是整个运行层。** 它不必作为一个单独的菜单出现；用户看到的是“协同”“夜间”“日历”这些可理解的入口。

## 4. 关键机制：推荐方案与论证

每项都写明：推荐方案、依据、替代方案、承重假设、最小验证、改线条件。

### 4.1 Skill 公用池：发布与挂载

**推荐方案**

- 工作台资产库是 Skill 的权威来源。
- “发布”就是把某个固定版本写入 `~/.agents/skills/<名称>`，并在工作台里登记发布记录（版本、指纹、时间）。
- 各 Agent 的接入方式：
  - Codex 原生读取 `~/.agents/skills`，不需要额外操作。
  - Claude 和 Hermes 在各自的 skills 目录下建立链接，挂载粒度可以是单个 Skill，也可以是一个套装。
- 默认规则：新收录的第三方 Skill 只收录、不发布、不挂载。通过安全检查后，由你决定挂给谁。
- 复制口令继续保留，适用于不支持挂载的 Agent、远程环境或临时使用。

**依据**

- 你已经在用“共享池 + 链接”的方式。
- Codex 官方读取 `$HOME/.agents/skills`：[官方文档](https://developers.openai.com/codex/skills)。
- 按 Agent 挂载可以控制每个 Agent 的上下文负担，因为每个 Skill 的描述都会进入提示词。

**本机现状与断链处理**

- 现状：`~/.claude/skills` 和 `~/.hermes/skills` 各有 233 个失效链接，来自一个已删除的第三方整包；Hermes 另有 31 个独立副本，Codex 有 25 个独立副本。
- 处理顺序：先由能力体检出一份只读报告，列出失效、独立副本和重复项；再由你逐批决定清理、找回还是纳入池子。**不自动删除任何东西**，清理属于 🔐 真实系统写入。

**替代方案**

- 只用复制口令：无法解决散落和断链的问题。
- 全量共享：会让 Agent 的上下文膨胀，第三方 Skill 也未经检查就生效。

**承重假设**

- Codex 新会话能稳定发现 `~/.agents/skills`。社区报告过发现不了的情况：[讨论帖](https://community.openai.com/t/local-skills-in-agents-skills-are-no-longer-discovered-in-new-codex-sessions/1379522)。
- Claude 和 Hermes 能按链接加载 Skill（本机已有 66 个有效链接，说明大致可行）。

**最小验证**

用一个合成 Skill 发布到共享池，在三个 Agent 的新会话里各确认一次能被发现。

**改线条件**

如果 Codex 的发现不稳定，Codex 改为写入 `~/.codex/skills`（官方保留的兼容位置），发布记录里标明写入位置。

### 4.2 能力体检与修复

**推荐方案**

- 体检只读，范围包括：
  - 各 Agent skills 目录的链接是否有效；
  - 挂载与发布记录是否一致；
  - 副本版本是否落后于池子；
  - Agent 的程序和配置是否可读；
  - Hermes gateway 是否在线。
- 结果进入收件箱，每条都附带“建议动作 + 影响 + 恢复方法”。
- 修复是另一件事：你在收件箱里确认后才执行。首批只做两类低风险动作：
  - 清理失效链接；
  - 按发布记录重建挂载。
- 执行后复验，并保留恢复记录。

**依据**

蓝图要求一键修复先覆盖“已验证的故障类型”；断链就是现成的、可验证的第一类故障。

**边界**

- 不改 Agent 的主配置。
- 未知故障只做诊断，不自动试错。

**最小验证**

在合成目录里造出断链、错位挂载和过期副本，检查体检能分别识别，修复后复验通过。

### 4.3 协同模式

**定义**

协同模式是带角色的工作流：
- 规定哪些 Agent 扮演什么角色；
- 什么时候交接；
- 交接时带什么（目标、最新纠正、权限、成果、下一步）；
- 谁拥有写入权；
- 失败了怎么办。

**首批两种**

1. **接力**：一段时间内只有一方写入，另一方可以只读复核，交接时带齐状态。本项目的 CURRENT/COLLABORATION 协议就是它的第一版实物。
   - **a 层（先做）**：工作台展示每个项目当前的写入者、状态编号和最新交接，生成“读 CURRENT 继续”这类交接口令供你复制。
   - **b 层（随后）**：交接后自动通知另一方。
   - **c 层（自动唤醒另一方开工）**：等单目标执行和监工闭环可靠之后再做。
2. **执行+监工**：Codex 是执行现场，Hermes 在后台审核阶段开工、阶段退出和完成声明；退回后自动返工，再复核。
   - 已有成果：试点 `supervisor_v1` 真机跑通过一次。
   - 推进方式：先在你选定的一个真实项目上跑通，再作为工作台里的一条协同工作流接入，工作台显示绑定、阶段、审查和异常。

**依据**

两种模式都有真实使用或代码基础，把它们整合进来不是从零开始。

**承重假设**

- 接力 b 层需要一个可靠的消息通道。Codex App Server 和 Hermes 的能力都要按动作逐项实测。
- 监工试点的两处竞态修正尚未在真机上重新验收（见试点 T07）。

**改线条件**

如果监工在真实项目中增加的负担多于减少的，就降级为“阶段完成时手动发起审查”，但保留状态账本。

### 4.4 运行层起点：Hermes 定时 + 工作台控制面（夜间）

**推荐方案**

- **分工**：
  - Hermes 的定时任务负责实际执行和执行记录，gateway 每 60 秒检查一次，记录写入 `~/.hermes/cron/executions.db`，每次执行有 claimed / running / completed / failed / unknown 几种状态：[官方文档](https://hermes-agent.nousresearch.com/docs/user-guide/features/cron)。
  - 工作台负责：定义任务（输入、允许修改的范围、成功标准、终止条件、预算），执行前预检，只读展示执行记录和成果，晨间接管进收件箱。
- **首批任务**：
  - 能力体检（只读）；
  - 知识整理候选（只产生候选，不写正式知识）。
- **防休眠**：只在任务窗口内生效，例如用 `caffeinate` 包住执行过程。
- **时间来源**：夜间窗口从工作台日历里安排（§4.5）。

**依据**

- 不重写执行内核（N3）。
- Hermes 已具备调度和执行台账。
- 首批任务风险低，晨间也容易验收。

**替代方案**

- 工作台自建调度器：重复造轮子。
- `launchd` + `codex exec`：可以作为“需要 Codex 执行的任务”的补充通道。

**承重假设**

- Hermes gateway 能作为服务长期运行。
- 执行记录的格式可以被稳定只读。
- 睡眠、网络中断、认证失效时，状态能如实落为 failed 或 unknown，而不是假成功。

**最小验证**

建一个合成的“只读体检”定时任务，完成一次“正常执行 → 故意断网或休眠 → 晨间查看”，看结果能否区分成功、失败和未知。

🔐 需要授权的事项：启用 Hermes gateway 服务、创建定时任务。这些都属于真实 Agent 配置。

### 4.5 工作台日历（时间规划本）

**用途（按你的原话）**

提前把自己的规划记下来，什么时间做什么，像备忘录一样一眼看清安排。

**推荐方案**

- **视图**：
  - 以“周视图 + 今天”为主；
  - 可以直接在时间轴上拖出一个**时间块**并写一句话；
  - 时间块可以关联项目、资产或夜间任务。
- **内容类型**：
  - 规划块：你自己写的，这是主要用途；
  - 会议；
  - 项目里程碑和截止日期；
  - 夜间窗口；
  - 提醒。
- **数据源**：macOS 日历。
  - 工作台新建或修改的条目写回 macOS 日历，写完回读核对；
  - 通过 iCloud，手机上也能看到并收到提醒；
  - 建议单独建一个“工作台”日历，用来放规划块和夜间窗口，与已有的会议日历分开，出问题时可以整体停用。
- **技术路线（待验证）**：
  - 工作台是本机 Node 服务，不能直接调用 macOS 的日历接口（EventKit），需要一个本机小助手程序，负责申请日历权限、读写和回读；
  - 替代路线是通过 AppleScript 操作“日历”应用，但速度和稳定性较差。

**依据**

- 符合“原件留原处”：权威仍在 macOS 日历。
- 满足“以后都看工作台”。
- 手机提醒不丢。

**承重假设**

- 小助手程序能获得并保持日历权限。
- 在工作台和“日历”应用两边都修改时，冲突可以用“以回读为准 + 提示”处理。

**最小验证**

在一个测试用的日历里完成“新建 → 回读 → 在‘日历’应用里修改 → 工作台刷新”全过程。

🔐 需要授权：日历访问权限、创建“工作台”日历。

### 4.6 进化回路与收件箱

**回路**

1. **使用证据**（1.1 已有）：复制成功才计次，并记录“好用 / 需改进”和备注。
2. **改版候选**：对标记“需改进”的资产一键“生成改版”，任务进入夜间队列，由指定 Agent 按原版、反馈和备注生成候选。
3. **比较**：候选出现在收件箱，与当前版本并排比较差异。
4. **采用或退回**：采用即生成新版本（历史不可变）；之后的使用证据会检验新版本是否更好；更差就恢复旧版，恢复本身也生成一个新版本。
5. **回收**：体检或夜间任务发现新的 Skill、方法（例如某个 Agent 新写了一个 Skill，或项目交接里沉淀出一套做法），先进收件箱，你确认后入池。

**“进化是否发生”的证明方式**（对应关键问题 5）

- 不看候选数量。
- 看被采用的改版在之后的使用中，“需改进”比例是否下降、复用次数是否上升，以及恢复旧版的次数。
- 按资产逐个展示，不做总体仪表盘。

**收件箱**

- 所有需要你判断的事项都进这里：体检、候选、回收、夜间结果、协同退回、知识候选、来源变化。
- 收件箱只做汇总和跳转，**在对应页面里执行动作**。这沿用 PRD §8.3 的原则。

### 4.7 规则模板：托管区块

**推荐方案**

- 模板内容：项目协同协议（入口文件、CURRENT 格式、认领与交接规则、验证与证据要求）。
- 装入方式：在项目的 `AGENTS.md`/`CLAUDE.md` 里插入一段有起止标记的区块，工作台只维护区块内的内容。
- 更新流程：预览差异 → 你确认 → 写入 → 回读。
- 模板本身有版本；每个项目记录自己装的是哪个版本；模板更新后，在收件箱提示“哪些项目可以升级”。

**依据**

这样所有 AI 在所有项目里遵循同一套逻辑（D10），同时不会覆盖某个项目的特殊规则。

🔐 需要授权：写入真实项目的文件。

### 4.8 贯穿能力：成本用量、操作留痕、常驻与备份

- **成本与用量**：先汇总各执行来源自报的用量，包括 Hermes 执行记录和各 Agent 的用量接口，按任务、Agent、模型展示；夜间任务按预算上限停止。**只展示来源里实际有的数据，拿不到的标为“未知”，不做估算。**
- **操作留痕**：以项目为单位，记录哪个 Agent 在何时认领、改了哪些文件（按文件指纹）、交接给了谁。来源是协同协议里的认领和交接记录，以及工作台自己的写操作日志；不读私人会话。
- **常驻**：用 macOS 登录项（LaunchAgent）让工作台开机即运行，异常退出自动重启。这是日历提醒和夜间运行的前提。🔐
- **完整备份**：备份范围是整个数据目录，包括主库快照、配置操作日志和知识写入日志，恢复时先预览；普通导出保持现状。

## 7. 承重假设与改线条件（新增部分）

| 优先级 | 假设 | 如果出现什么就改线 | 最小验证 |
|---|---|---|---|
| 1 | 用户会把工作台作为每日入口（日历 + 收件箱） | 实际仍主要看“日历”应用和各 Agent，工作台很少打开 | 第三阶段后记录一周的真实打开情况；由你判断 |
| 2 | 发布 + 挂载能稳定地让三个 Agent 发现 Skill | 某个 Agent 发现不稳定 | §4.1 合成验证；该 Agent 退回复制口令 |
| 3 | Hermes 定时能可靠地在夜间运行并如实记账 | 结果经常显示未知，晨间复核成本高于收益 | §4.4 中断试验；收窄任务或改用 `launchd` |
| 4 | 本机小助手程序能稳定读写 macOS 日历 | 权限被撤销，或两边同时修改导致冲突频发 | §4.5 测试日历；退回“只读显示 + 在‘日历’应用里编辑” |
| 5 | 监工在真实项目中减少而不是增加你的负担 | 等待和误退回多于有效拦截 | 在一个真实项目上试跑；降级为手动发起审查 |

## 8. 不做的事（本版明确）

- 近期不做 Agent 自发协同（N1）。
- 飞书不做双向同步（N2）。
- 不重写 Agent 执行内核（N3）。
- 不代替 Agent 的记忆（N4）。
- 日历不替代 macOS 日历的存储，也不做团队排期。
- 收件箱只做汇总和跳转，不在收件箱里直接执行动作。
- 不做全局仪表盘或总体完成度百分比。
