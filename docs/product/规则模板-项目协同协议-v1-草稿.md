## 多 Agent 协同协议

本项目可能由多个 Agent（如 Codex、Claude、Hermes）轮流工作。以下规则对所有 Agent 生效；与系统指令或用户当轮指令冲突时，以它们为准。

### 1. 唯一状态

- 项目根目录的 `CURRENT.md` 是唯一的实时状态。聊天记录、旧交接文件都不是。
- `CURRENT.md` 顶部至少有这几项：

  | 字段 | 含义 |
  |---|---|
  | 状态编号 | 每次状态有实质变化就递增，例如 `P-20260929-03`，旧编号不复用 |
  | 当前写入者 | 正在改文件的 Agent；没有则写“无” |
  | 当前任务 | 一句话 |
  | 最新交接 | 指向最新一份交接文件 |
  | 唯一下一步 | 只写一件事 |
  | 各 Agent 已读 | 每个 Agent 最近一次读回并核对过的状态编号 |

- 项目还没有 `CURRENT.md` 时，先征得用户同意，再按上表创建。

### 2. 开工

1. 读 `CURRENT.md` 和它指向的最新交接，记下状态编号。
2. 核对交接里说的文件与实际一致；对不上时先报告，不要接着改。
3. 已有其他写入者：只做只读检查，或等交接。不要因为对方看起来空闲就接管；需要接管时由用户安排。
4. 无人写入：先在 `CURRENT.md` 登记本轮 Agent、任务、拟修改的文件范围和验证方式，递增状态编号，回读确认后再改其他文件。

### 3. 工作中

- 同一时间只有一个写入者；另一方可以只读复核。
- 每开始一批新的写入前，都重新读 `CURRENT.md`，确认登记仍是自己的；扩大修改范围、运行会批量改文件的命令（格式化、构建、依赖安装）前同样要确认。登记已被改动时先停下，读新交接。
- 每次编辑一个文件前，确认它和你上次看到的一样；发现超出预期的变化，不要整文件覆盖，先查明来源。
- 两方几乎同时认领、出现来源不明的变化，或写入者身份对不上时，立即停止业务写入，先和用户或另一方对齐。这只是协作约定，没有系统锁，不能用“我先看到空闲”作为覆盖的理由。
- 保留用户和其他 Agent 的未完成改动；不批量清理、重置、覆盖不属于本轮的文件。
- 改动前保存要改文件的原样副本或记下其指纹，便于复核和恢复。
- 结果不明（中断、超时、响应丢失）时，先查文件和记录的实际状态，不盲目重试写入。
- 读取私人资料、写入真实外部系统、安装第三方组件、使用付费服务、提交或推送，都需要用户当轮明确授权；以前的授权不自动延续。

### 4. 发现问题

按三类报告，不混在一起：**已复现的缺陷**（附复现步骤）、**有证据的维护债**、**待验证的建议**。复核意见要绑定具体的文件版本；被复核的内容之后又改了，旧结论不自动适用。

### 5. 完工交接

1. 按项目约定的方式验证，保存结果；没做的检查写明原因。
2. 新建一份交接文件（不覆盖旧的），至少写：输入与输出状态编号、执行者与范围、改动文件、验证结果及证据位置、真实数据是否变化、未完成项与风险、权限边界、唯一下一步。
3. 更新 `CURRENT.md`：新状态编号、最新交接、唯一下一步；工作真正结束才把写入者改为“无”。回读确认。
4. 答复用户时给出状态编号和交接文件路径。按项目实际情况通知另一方：只有已核实可用、并经用户授权的消息通道才可以直接发交接指针；没有这样的通道时，说明“已写入共享状态，需要用户转告另一方读取”。
5. 不替另一方声称“已读”“已接手”或“已通过”；只填自己的已读记录。

### 6. 证据分层

以下是五件不同的事，分别报告，不用其中一件代替另一件：文件已修改 / 自动检查通过 / 运行中的服务已采用 / 真实使用过 / 用户已验收。版本号、页面存在、测试数量都不等于完成。

## 修订说明（相对初稿）

| 初稿审阅点 | 修订决定 | 理由 |
|---|---|---|
| 小项目要不要保留状态编号 | **保留，但只要求“有实质变化就递增”**，并给出 CURRENT 最小字段表 | 状态编号是“已读确认”能对得上的唯一依据；本项目两个 Agent 多次靠它发现对方是否读到最新状态。成本只是一行 |
| “先写测试再修”对非代码项目不适用 | **从本模板移出**，改为“按项目约定的方式验证”；代码相关要求留给后续单独的“代码项目规范”模板 | 本模板只管协作，不管具体怎么干活；这样文档、调研、设计项目也能直接装 |
| 项目特有内容 | 不写入模板，留在各项目区块外 | 与托管区块的设计一致 |

另外补充了初稿没有、但本项目实际踩过的点：CURRENT 不存在时怎么办（先问用户）；结果不明先查实际状态；问题分三类报告、复核绑定版本；按实际通道通知另一方；不替另一方代签。
