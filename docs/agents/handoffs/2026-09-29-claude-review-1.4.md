## 3. 复核要点（对应 Codex 列出的四项）

1. **测试没有被削弱，也没有用延时掩盖 D-KM。**
   - 原来的同步点等待的是一条“整理任务已刷新”的提示，但页面上还留着上一次刷新的同一条提示，所以会误命中。这正是 D-KM 的根因。
   - 现在先注册响应等待器，再控制两种返回顺序，断言以“本次响应返回，并且按钮恢复”为准。没有加入固定延时。
   - refresh-first 分支最后的“旧报告没有出现”，只在网络完成后等了两帧渲染。之所以足够，是因为产品代码在结构上就丢弃过期结果：刷新完成后 `refreshEpoch` 增加，`identity` 随之改变、序号前移，迟到的结果过不了 `current()` 判断；而且 `setReport` 在请求返回后同步执行，没有延后执行的路径。
2. **验收矩阵充分。** [QA-v0.17](../../../QA-v0.17.md) 共 31 行，每行契约都有测试和结论。Codex 请我重点看的几项都有专门用例：
   - 预览上限 30 份、任务上限 50 个；
   - 同字节的文件或目录被替换后，旧预览失效，身份需要重新捕获；
   - 部分依据变化时，只列出相关的主张、冲突和关系；
   - saved / withdrawn / pending 三类记录分开处理；
   - 进行中的预览会被恢复查询作废；
   - 恢复入口同样要求会话凭证。

   矩阵也如实写明了哪些是组合约束得出的上限，而不是专门测过的基准。
3. **三类恢复区分清楚。**
   - 普通 workspace 刷新返回 503：保留带时间的旧报告，不推进，重试成功后才清除。
   - recover 返回 503：保持“待核对”，禁用创建，create 调用次数始终为 1。
   - 提交成功但响应丢失：按固定请求 ID 找回，不会重复创建。

   “真实重载”这个分支已改为真正执行 `page.reload()`，然后通过已保存的父子关联（“查看后续任务”）找回，不再依赖组件内存。被删掉的“点预览 → 提示‘整理记录已更新’”这一步，只在旧的伪重载路径下才会出现，删除它不算放宽断言。按契约，原任务可以有多个后续任务，重载后再次预览属于正常的新建路径，仍需要你确认。
4. **焦点样式只影响知识确认框。** 关键流程在五种宽度下都没有回归，dist 与 Codex 的 T2 隔离构建一致。
